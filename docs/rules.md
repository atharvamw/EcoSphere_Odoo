# EcoSphere — Rules & Conventions (SOP for Developers & AI Agents)

This file is the standard operating procedure for anyone — human or AI — building or modifying EcoSphere. It covers business rules that must not be broken, conventions that should be followed by default, and guardrails on what to avoid doing without explicit confirmation. It does **not** attempt to close off future flexibility — where something isn't decided yet, that's flagged as "open," not banned.

---

## 1. Core Business Rules (non-negotiable)

These come directly from the product's operating logic. Breaking them produces incorrect ESG data, which is the one thing this product cannot get wrong.

### 1.1 Data model
- **Master Data vs Transactional Data are distinct layers.** Master Data (Department, Category, Emission Factor, Product ESG Profile, Environmental Goal, ESG Policy, Badge, Reward) is configuration; Transactional Data (Carbon Transaction, CSR Activity, Employee Participation, Challenge, Challenge Participation, Policy Acknowledgement, Audit, Compliance Issue, Department Score) is generated by activity. Transactional records must always reference valid, non-deleted Master records — never store free-text duplicates of master fields.
- **Department is the organizational anchor.** Every score, transaction, and participation record must trace back to a Department, since Department Score is the aggregation unit.

### 1.2 Scoring
- Score aggregation is fixed as: **Transaction/Activity data → Environmental / Social / Governance Score → Department Total Score → Overall ESG Score.**
- Default weighting is **Environmental 40% / Social 30% / Governance 30%**, but this **must be configurable per organization** in Settings — never hardcode the weighting in application logic. Read it from ESG Configuration at calculation time.
- Score calculations must be re-runnable/auditable — never overwrite a historical Department Score in place; store it as a point-in-time record so historical reports remain accurate even if weighting changes later.

### 1.3 Carbon accounting
- Carbon Transactions require an Emission Factor. When **Auto Emission Calculation** is enabled (Settings toggle), Carbon Transactions must be derived automatically from linked Purchase/Manufacturing/Expense/Fleet records — no manual entry required, but manual override should remain possible for corrections (log the override, don't silently allow it).
- When Auto Emission Calculation is **disabled**, Carbon Transactions must be entered manually — do not silently fall back to auto-calculation.

### 1.4 CSR / Evidence
- When **Evidence Requirement** is enabled (Settings toggle), an Employee Participation record **cannot** be marked Approved without an attached proof file. This check happens at approval time, not at submission time — submission without proof should still be allowed as a draft/pending state.

### 1.5 Gamification
- Challenge lifecycle is strictly: **Draft → Active → Under Review → Completed**, or **Archived** (from any state). Do not introduce additional states without updating this SOP first — downstream reporting depends on this exact set.
- When **Badge Auto-Award** is enabled, a Badge must be assigned automatically the instant an employee's XP, completed-challenge count, or other tracked metric satisfies that Badge's Unlock Rule. This must be evaluated as a side effect of the event that changes the metric (XP award, challenge completion) — not on a delayed batch job, unless the org has no real-time requirement.
- **Reward Redemption:** redeeming a Reward deducts Points from the employee's balance and must check stock availability first. A redemption that would take stock negative, or points negative, must be rejected — never allow negative stock or negative point balances.

### 1.6 Governance & compliance
- Every Compliance Issue **must** have an assigned Owner and a Due Date at creation — these are not optional fields, even though they may look optional in a generic CRUD form.
- A Compliance Issue that passes its Due Date while still Open must be flagged/escalated — this feeds the Notification System (see 1.7). This should be a scheduled check, not something the user has to notice manually.

### 1.7 Notifications
- The platform must send notifications (in-app and/or email, per Notification Settings) for at minimum: new Compliance Issue raised, CSR/Challenge approval decisions, policy acknowledgement reminders, badge unlocks. Treat this list as a floor, not a ceiling — additional notification types are welcome, but these four must never be silently dropped.

### 1.8 Reporting
- All reports (Environmental, Social, Governance, ESG Summary, Custom Report Builder) must support filtering by: Department, Date Range, Module, Employee, Challenge, ESG Category — and export to PDF / Excel / CSV. Don't ship a report screen that's missing filter support to "add later" without flagging it.

## 2. Conventions to Follow

### 2.1 Naming
- Use the domain vocabulary exactly as defined in the product doc (Department, Category, Emission Factor, Carbon Transaction, CSR Activity, Employee Participation, Challenge, Challenge Participation, Policy Acknowledgement, Audit, Compliance Issue, Department Score). Don't rename these in code, API routes, or UI copy to synonyms (e.g. "Task" instead of "Challenge") — consistency here is what keeps reports, filters, and docs aligned.
- API routes: REST, resource-based, plural nouns (`/departments`, `/carbon-transactions`, `/challenges/:id/participations`).
- Database tables: snake_case, singular-domain-plural-table (`departments`, `carbon_transactions`).
- Booleans/toggles in Settings should read as an on/off statement of the rule they gate (`auto_emission_calculation_enabled`, `evidence_requirement_enabled`, `badge_auto_award_enabled`) — mirrors the four toggles defined in the spec, so new ones should follow the same `_enabled` suffix pattern.

### 2.2 Architecture defaults (open to change, but this is the default assumption)
- Relational database (PostgreSQL) — the domain is heavily relational (Master ↔ Transactional, Department hierarchy, scoring rollups).
- Backend: REST or GraphQL API, role-based access control (Admin / ESG Manager / Department Head / Employee, at minimum).
- Score calculation logic lives server-side only — never trust a client-submitted score.
- File uploads (CSR proof, audit evidence) go to object storage, not the database.

### 2.3 Workflow states
- Anything with a lifecycle (Challenge, Compliance Issue, Employee/Challenge Participation approvals) should use an explicit `status` enum field, not booleans (`is_approved`, `is_active`) stacked on top of each other — this avoids invalid state combinations.

### 2.4 Auditability
- Score history, badge awards, reward redemptions, and compliance status changes should be append-only / logged, not just updated in place. ESG data has compliance implications — organizations will need to answer "what was our score on this date" and "who approved this and when."

## 3. What the AI Agent Should Not Do Without Confirmation

These aren't permanent bans — they're points where the cost of guessing wrong is high, so check first rather than assume.

- **Don't silently change the default ESG weighting (40/30/30)** or hardcode it anywhere — always read from configuration, and don't alter the default without being asked.
- **Don't remove or rename the four Settings toggles** (Auto Emission Calculation, Evidence Requirement, Badge Auto-Award, and the implicit Notification Settings toggle group) — they're explicitly "in scope, not optional" per the product spec.
- **Don't invent new Challenge/Compliance Issue lifecycle states** without flagging it — reporting and filters depend on the fixed enum.
- **Don't expose scoring/calculation logic to the client** (e.g. computing scores in frontend JS) — always compute server-side.
- **Don't auto-approve** CSR Activity or Challenge Participation records — approval is a human governance action, even when Evidence Requirement is off.
- **Don't allow negative point/XP balances or negative reward stock** — reject the operation instead of clamping silently.
- **Don't drop compliance-critical fields** (Compliance Issue Owner, Due Date) to "simplify" a form — they're mandatory by spec, not by convenience.
- **Don't design gamification mechanics that gate access to Environmental/Social/Governance core reporting features** — gamification is an engagement layer on top of ESG tracking, not a paywall inside it.

If a request seems to require going against one of the rules in Section 1, flag the conflict explicitly rather than quietly picking one side.

## 4. Open / Undecided (deliberately not restricted)

These are real gaps in the current spec — don't treat their absence as a rule. Ask, or make a clearly-labeled assumption and proceed:

- Exact multi-tenancy model (single org vs multi-org SaaS) — not specified.
- Detailed role/permission matrix beyond the implied Admin/Manager/Employee split.
- Mobile app vs. mobile-responsive web only (spec lists mobile-responsive as a "bonus idea," not a requirement).
- Specific emission factor data sources/standards (e.g. GHG Protocol, DEFRA) — not specified in the source doc; will need to be sourced and cited when implemented.
- Real-time vs. batch score recalculation cadence.

## 5. How to Use This Document

- `brand.md` governs **how it looks**. `rules.md` governs **how it behaves and how it's built**. Both should be treated as living documents — update them explicitly (with a short changelog note) rather than drifting from them silently as the project evolves.
- When a request conflicts with something here, say so before proceeding, rather than resolving the conflict silently in one direction.
